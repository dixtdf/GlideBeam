# 当前 NVENC 模块的兼容处理

在这台 RTX 3060 12GB 黑苹果上，普通颜色采样不足以证明桌面编码正确。细线图案暴露出空间位置丢失、重复和错位；换软件 H.264 编码后同一图案正常。复测排除了复用采集缓冲、异步回调和关键帧请求的影响。

对已发布二进制的地址规律分析，以及随后逐像素内容检查，支持 NV12 上传布局与 GPU 读取布局不一致。应用在送入编码器前复制并预排列 Y/UV 平面，分别按 8/16 字节组处理。采集源保持只读；目标缓冲保留到编码回调完成。为容纳 UV 平面边界，编码高度从 1080 补齐至 1088，补齐行重复最后一行，Windows 按帧头的可见尺寸裁剪回 1920×1080。

补偿只在两个条件同时成立时启用：

- 实际选择的编码器为 `com.nvmtl.videoencoder.avc.nvenc`。
- dyld 已加载的 `libnvenc_h264.dylib` 的 SHA-256 为 `164f6dfa409352e90b079659578a012dc37d1fba364067b99cb8c7bf337b1b5d`。

SHA-256 来自实际映射路径，按进程缓存。未来模块版本不会自动套用这项补偿，须重新做图案验证。该处理未修改驱动、TCC 数据库或 SIP 配置。当前只验证 1920×1080；显示器分辨率改变需要另行验证。

生产 Agent 的 12 帧硬编码自检通过 Apple 软件解码核对内容：分布采样 Y 平均绝对误差 0、UV 平均绝对误差约 0.0083，密集色度位置检查错误数 0，薄线移动及底部行通过。强制 IDR 检查通过。Windows 随后以 GPU 解码同一测试流并呈现 12 帧。详细结果见 `validation.md`。

HEVC 内容校验未通过，因此首版使用 H.264。当前模块的码率设置不能据此视为完整码率控制；已知实现使用固定 QP 23，实际带宽随内容变化。这里不承诺 4:4:4 彩色文字保真，H.264 NV12 仍是 4:2:0。
