# Transport implementation

The `remote_transport` Rust library exports the C interface in `shared/protocol.h` as both a static library and a dynamic library. It uses Quinn 0.11 and rustls 0.23 with ring; the dependency versions are fixed in `Cargo.lock`.

## Authentication and identity

`remote_server_start("0.0.0.0:47990", pairing_token, identity_directory)` creates a persistent self-signed certificate and key in that directory. On macOS the private key is created with mode `0600`. Incomplete or mismatched existing identities are rejected; the library never silently generates a different identity on restart. Protect the identity directory using the user's account permissions.

The Windows user supplies only a numeric address and pairing token. A token may be any 6–128 Unicode characters without control characters; it may be generated or customized and persisted by the host. The Windows client protects its saved token with the current user's DPAPI. The Mac host owns its private token file; changing it updates the server in memory and immediately closes current or pending authenticated connections.

Control pairing uses [RustCrypto SPAKE2 0.4](https://docs.rs/spake2/0.4.0/spake2/) with Ed25519Group and fresh random values. It exchanges masked 33-byte curve messages, never the plaintext token, then verifies mutual HMAC-SHA256 key confirmations bound to both PAKE messages, directional roles, the random 128-bit session ID, and the QUIC TLS exporter. Received points must be canonical, prime-order, and non-small-order. Application channels are enabled only after both confirmations. The token is not exposed to a first-use self-signed TLS peer or a passive observer; different TLS sessions cannot relay the confirmation unchanged.

The legacy client certificate-pin argument is optional (empty or null enables PAKE-only first use). An explicitly supplied pin still requires 64 SHA-256 hex digits, optionally separated by colons. TLS CertificateVerify signatures are always checked. After successful PAKE, `remote_fingerprint` exposes the authenticated server's certificate digest; media and bulk connections are automatically pinned to that exact certificate. The standard Windows UI does not require a fingerprint. It records the authenticated fingerprint internally, while the token authenticates each subsequent control connection.

Only a completed, incorrect control-channel password proof increments the source IP's counter, once per logical attempt. Success clears an unblocked IP's counter. The tenth consecutive error blocks the IP; blocked addresses are rejected before TLS pairing and remain blocked until the host user removes them. TLS/pin errors, malformed or incomplete messages, timeouts, disconnected networks, a wrong media capability, and capture/codec errors do not consume password attempts. Counters and blocks persist in `identity_directory/auth-policy.json` (mode `0600` on macOS), using a flushed atomic replacement. A corrupt policy file fails startup instead of resetting bans. Entries are bounded to 4,096 and the policy file to 1 MiB.

## Wire layout

One client session consists of two required QUIC connections and one optional independent synchronization connection, sharing one UDP endpoint/port:

- Input connection: channels 1, 2, and 3 each use their own reliable ordered unidirectional stream. The stream starts with a one-byte channel ID; each message uses a little-endian `uint32` length followed by that many payload bytes. Reliable messages are limited to 1 MiB.
- Media connection: channel 4 uses negotiated QUIC datagrams. Every fragment has a 24-byte header: magic `RDG1`, frame sequence (`uint64`), fragment index/count (`uint16` each), complete byte length (`uint32`), payload stride (`uint16`), and reserved (`uint16`). All integers are little-endian. The payload includes the complete `RemoteFrameHeader` from the shared header.
- Optional system audio shares the authenticated media connection after a CONTROL `audio-start` request with integer `version:1`. A 992-byte `RFA1` datagram contains a packed 32-byte `RemoteAudioHeader` and 240 stereo signed-PCM16 frames at 48 kHz (5 ms). It is never fragmented or retransmitted. A separate eight-packet queue accommodates capture bursts while expiring packets after 20 ms of actual queue waiting; audio is scheduled before each video fragment. The send buffer is 4 KiB. Audio APIs do not share `remote_poll` or video recovery state. Subscription permission is reset on every session and `audio-stop` clears it, preserving old viewers.
- Bulk connection: clipboard/file synchronization uses separate bidirectional reliable streams and separate C API queues. Each side opens one sending stream starting with `BUL1`; frames use a little-endian `uint32` length and 1–1 MiB payload. The receiver writes a one-byte `1` acknowledgement after admitting a complete frame to its bounded queue. The sender waits for this acknowledgement before writing another frame. The acknowledgement does not mean that the application processed the payload or persisted a file; application-level acknowledgement is still required. Duplicate streams and invalid frame lengths close only bulk.

Authentication uses one bidirectional stream before application channels. ALPN is `remote-flat/2`. The common header is magic `RMC2`, a one-byte role (1 control, 2 media, 3 optional bulk), and 16 session-ID bytes, with no token length or token bytes. The control/media wire contract is unchanged: old two-connection clients work with the new server; a new client connecting to an old server keeps remote control available when bulk is refused.

For control, the client appends its 33-byte SPAKE2 message; the server replies with its 33-byte message. The client sends a 32-byte `client` confirmation and finishes its stream. After verifying it, the server sends its 32-byte `server` confirmation, a fresh random 32-byte media capability (covered by the server confirmation), and the one-byte session acceptance flag, then finishes. Media starts only after the control proof succeeds: it sends the common header plus `HMAC(media_capability, media_role || media_TLS_exporter || session_ID)`. The server accepts that one-use capability only for the same control session and IP, replies with the acceptance flag, then starts application traffic. Media never creates a second password guess. One paired client is supported.

Bulk starts asynchronously after control/media readiness. Its distinct 32-byte capability is `HMAC-SHA256(media_capability, "bulk-capability/v1" || control_TLS_exporter || session_ID)`, derived only after successful mutual PAKE. Its hello appends `HMAC-SHA256(bulk_capability, "bulk/v1" || bulk_TLS_exporter || session_ID)`. The server requires role 3, the existing authenticated session/IP and unchanged token generation, validates the proof and stream end, then replies with a one-byte acceptance flag. A media capability/proof cannot authorize bulk. A captured bulk proof cannot be replayed on another TLS connection. No bulk failure increments token-guess counters. One active bulk connection is allowed; token rotation and parent session disconnect revoke it immediately. Within a live control session the client retries failed bulk with exponential backoff (1–30 seconds), deriving a fresh TLS-bound proof; queued old bulk payloads are cleared before the next generation. Applications must reset their synchronization generation and negotiate/resume transfers explicitly rather than assuming old messages were delivered.

## Bounds and video recovery

Frames are limited to 8 MiB. Reassembly validates metadata, duplicate fragments, lengths, and dimensions; it holds at most three fragmented frames and expires incomplete frames after 120 ms. Completed frames are delivered in sequence. Missing frames, reassembly expiry, or receive queue overflow switch to waiting for an IDR and send a reliable `INPUT_KEYFRAME` request at most every 150 ms. P frames are withheld during recovery.

The video sender allows two queued encoded frames and uses `send_datagram_wait`, applying backpressure rather than silently evicting queued reference data. A frame has a 100 ms send deadline. Overload or an expired deadline returns an error / posts `INPUT_KEYFRAME` locally to the host, clears stale pending frames, and refuses subsequent P frames until an IDR is accepted. The encoder must honor this event by forcing an IDR carrying SPS/PPS. It must also handle a negative `remote_send` return.

Reliable queues are bounded to 256 messages and 32 MiB. Adjacent unsent mouse-move events are coalesced; coalescing never crosses a button or key event. Click events retain their coordinates. Reliable inbound queues apply backpressure without discarding messages. The viewer queue accepts up to three encoded video frames; falling behind initiates explicit IDR recovery rather than decoding a broken reference chain.

Bulk sending and receiving each have independent limits of 32 queued frames and 8 MiB. At most one additional frame per direction is in flight/being read. A full bulk receive queue pauses only bulk acknowledgement; it never consumes an input/video queue slot or blocks `remote_poll`. A full send queue returns retryable backpressure before copying the caller's buffer. Frames remain FIFO; prioritize short clipboard/control messages at the application scheduler and keep file chunks small (64 KiB). Independent QUIC connections still share network and disk resources: applications must pace file traffic, limit their own unacknowledged chunks and reduce the rate when input RTT/video pressure rises.

## C API behavior

`remote_audio_send(endpoint,data,len)` returns `1` accepted, `0` unsubscribed/expired/backpressured, or `-1` invalid/disconnected. It validates exactly 992 bytes, 48 kHz, two channels, 240 frames, the `RFA1` magic and flags (bit 0 discontinuity only). Queue overload discards the oldest packet and marks a discontinuity; the caller never retries obsolete sound. `remote_audio_poll` returns length/zero/error independently of video, retains the queue head when capacity is too small, and validates expiry. `remote_audio_pending` returns the received audio queue count. All require the same close/handle lifetime serialization as other APIs. An older DLL may lack these exports; the new Windows client loads audio optionally and keeps video working. See [audio capture and playback](audio.md).

Startup is asynchronous. `remote_status` is `0` while connecting/listening, `1` when both authenticated connections are ready, and `-1` for a terminal startup/client error. A server returns to status `0` after a disconnected session and listens for a new client. `remote_last_error` reports the most recent detailed diagnostic, including authentication failures and queue recovery. Invalid startup arguments return a null pointer.

`remote_send` returns `1` when accepted into the bounded queue and `-1` when not accepted. It does not mean the remote application has processed the message. Calls made before connection readiness are rejected.

`remote_poll` returns payload length, zero when no message is queued, or `-1` for an error. When capacity is insufficient the queue head is preserved; the error includes the required size. Allocate at least 8 MiB if polling video. Polling and sending may run on different threads. The application must serialize `remote_close` against all other calls using that handle; no calls are valid after close. `remote_close` signals cancellation, stops session tasks, and joins the worker thread. All exported entry points contain Rust panics.

`remote_rtt_ms` reports the input connection's actual QUIC smoothed network round-trip time in milliseconds, refreshed every 100 ms. It returns zero before connection readiness. This is network RTT, not capture-to-display latency or input response latency.

`remote_pending(endpoint, channel)` reports the actual count of fully assembled received messages awaiting application polling for that channel. It does not include fragmented packets or frames already submitted to the decoder.

`remote_bulk_status(endpoint)` is `0` while unavailable/connecting or outside a connected parent session, `1` while authenticated bulk is ready, and `-1` after an optional feature failure. Bulk readiness never gates `remote_status`. `remote_bulk_send(endpoint,data,len)` accepts 1–1 MiB frames and returns `1` queued, `0` full queue (retry without advancing transfer offsets), or `-1` invalid/unavailable. `remote_bulk_poll(endpoint,data,capacity)` returns a payload length, `0` empty, or `-1` for feature error/invalid arguments/insufficient capacity; a small buffer preserves the queue head. Allocate 1 MiB. `remote_bulk_pending` counts received frames awaiting bulk polling. Bulk never appears in `remote_poll` or `remote_pending`. All four functions follow the existing handle lifetime rule; serialize close against every call.

Server management APIs are thread-safe with poll/send: `remote_auth_policy_json` returns `{ "threshold": 10, "entries": [{ "ip": "10.0.0.1", "failures": 10, "blocked": true }] }`; its return length excludes the trailing NUL, and insufficient capacity returns `-1`. `remote_unblock_ip` removes both the block and its counter and returns `1` after persistence; an absent IP is also success. `remote_set_token` validates a new token, updates server memory, and closes existing/pending connections, returning `1`; the host must persist its token separately before calling it. These server-only APIs return `-1` on invalid arguments, client handles, or persistence failure. As with all APIs, the application must prevent concurrent `remote_close`.

The host application must release pressed keyboard/mouse buttons when status leaves connected. It must keep polling channel 2 to honor keyframe requests generated by send-side backpressure.

## Build and verification

Windows GNU release outputs are `target/release/remote_transport.dll`, `target/release/libremote_transport.dll.a`, and `target/release/libremote_transport.a`. macOS release output is `target/release/libremote_transport.a` (and `.dylib`). Static Windows linking also needs the platform system libraries used by Rust: `ws2_32`, `userenv`, `bcrypt`, `ntdll`, and `advapi32` as reported by the final linker. A DLL avoids inheriting those static system-library dependencies into the C++ client.

Run `cargo test -p remote_transport` and `cargo build --release -p remote_transport`. Tests cover custom Unicode tokens, PAKE mutual proofs and transcript/TLS/role/capability binding, wrong tokens and first-use fake servers, per-IP counters, success reset, the tenth-error threshold, ban persistence and unblock, live and idle token rotation, pin parsing, ordered move coalescing, bounded poll capacity, fragmented video, timeout recovery, and real encrypted UDP loopback sessions. Network tests verify empty-pin first use, no plaintext token sent to an untrusted first-use peer, no application readiness without a valid server proof, exactly one counter increment per wrong attempt, blocked rejection even with the correct token, management APIs, all reliable channels, multi-fragment video, identity persistence, and timely close. The idle-rotation regression repeatedly changes a token while the server is awaiting a connection and verifies the first new-generation client succeeds. Incomplete control and invalid media authentication do not increment the password counter. Bulk tests cover role/key/exporter separation, actual TLS proof replay rejection, invalid capability/session/oversized frames without password penalties, compatibility with legacy two-connection clients and servers, FIFO/poll retention and byte/count bounds, input/video delivery while bulk receive is saturated, two-way payloads, independent bulk interruption/reconnection with old queues cleared, and timely close while bulk is flow-controlled.

For an offline macOS build, `cargo vendor --locked --versioned-dirs build/vendor` and the resulting `build/vendor-config.toml` are provided. Copy its `[source]` configuration to `.cargo/config.toml`, preserve the `build/vendor` directory relative to the project root, and run `cargo build --release --locked --offline -p remote_transport`.

Audio tests cover strict versioned subscription, legacy and rapid reconnect isolation, packet validation, source-burst capacity, queue expiry, poll retention, and simultaneous encrypted audio/video/input with timely close.
